WHY STEP 13 IS INTENTIONAL
R24 expands support/financial access and Planning-only enforcement, but it also replaces several money RPCs. The canonical money migration is deliberately re-runnable and is applied again after R24 so the final database keeps R24's access functions while using the R27 quote, billing, charge-cancellation, VAT and invoice-visit authority.

WHY STEPS 15–17 ARE FINAL
The 7 Sep medium stress test exposed database defects that were being misreported or hidden by the UI: permanent PIN generation had an ambiguous team_id conflict target; secure document creation called pgcrypto without Supabase's extensions schema; the live R30 quote-prepayment reconciler had a PL/pgSQL record/alias collision; and routine charge-cancellations were not represented consistently in Billing review. R31 makes those repairs authoritative after every earlier migration.

The live TuinBooks database also contains a newer R29/R30 quote-prepayment layer that was not present in this repository. Steps 16–17 are deliberately conditional: when that layer exists they preserve its repaired invoice/prepayment and Billing-read behavior; when it does not exist they leave the R27 finance authority unchanged.

IMPORTANT SOURCE-PARITY NOTE
The live R29/R30 quote-prepayment feature set predates this recovery branch and was not found in repository history. Steps 16–17 preserve the repaired live behavior but do not pretend that the complete historical R29/R30 feature implementation has been reconstructed here. Do not use an older installer to overwrite a newer production database. Application source and database RPCs must move together.

The old statement that INSTALL-V2-CORE.sql alone represents the entire current database contract is no longer valid. It contains the eight base migrations only.
